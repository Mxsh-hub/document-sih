# Repository Audit — AstraVerify (`document-sih`)

**Audit date:** 2026-10-23
**Scope:** Entire repository at commit `07d2636b` plus uncommitted `AGENTS.md`.
**Purpose:** Establish an accurate baseline before adapting the repository to the AICTE application-validation problem statement (Phase 1 of `IMPLEMENTATION_ROADMAP.md`).

**Method:** Static review of every source file, manifest, configuration, committed artifact, and test; dependency installation in a local virtual environment; execution of both existing backend test scripts; inspection of produced runtime data. No application code was modified.

---

## 1. Executive summary

The repository is a functioning **demo prototype for privacy-preserving academic/professional credential verification**. It is not an application-validation or regulatory-compliance system.

- The strongest assets are the OCR pipeline, the FastAPI service skeleton, and the Groth16/blockchain plumbing. These are real and reusable.
- The marketing claims (AI forensics swarm, deepfake detection, cryptographic authenticity, immutable anchoring) are **substantially overstated**. Several components are constants or hardcoded data.
- The architecture required by the roadmap — applications, institutions, checklists, versioned rules, issuer verification adapters, anomaly detection, reviewer workflows, audit trail, authentication — is **entirely absent**. There is no application entity and no database.
- The ZK circuit is **unsound**: a prover can produce a "valid" proof for an arbitrary CGPA.
- The backend reports successful ZK verification **without verifying the proof at all**.

**Verdict:** Reusable foundation, but Phases 3–8 of the roadmap are greenfield work. The existing product surface should be treated as a reference implementation and source of components, not as a base to incrementally extend.

## 4. What actually works

1. **File upload** persists a UUID-named file and a metadata record.
2. **OCR** extracts text from text PDFs, scanned PDFs, and images. Verified by the integration test.
3. **Field extraction** recovers CGPA, degree, roll number, year, and name in favourable layouts, but is regex-only and layout-sensitive.
4. **PDF forensics heuristics** inspect producer/creator metadata, font count, and circle detection. They run and produce plausible scores but are not validated against labeled tampered documents.
5. **Orchestrator** applies deterministic thresholds and assigns `PASS` / `FAIL` / `MANUAL_REVIEW` and a tier.
6. **Attestation** emits a W3C-shaped VC and an HMAC signature.
7. **Client-side Groth16 proving/verification** works if the committed wasm/zkey/vkey match and `window.snarkjs` loaded.
8. **Hardhat contracts and deployment artifacts exist**; the frontend can anchor a hash through MetaMask. Deployment was not re-executed during this audit (see §14).
9. **Three-portal React app** renders and routes correctly.

Additional integrity gaps:

- **No document hash at upload.** A hash exists only for the issued VC, so file integrity cannot be checked later.
- **No document classification.** The pipeline assumes everything is a degree certificate.
- **No page references or confidence scores** in extraction output.
- **OCR name extraction is demonstrably wrong.** The committed metadata shows `"name": "John Doe\nCGPA"` because the regex allows `\s` to cross line boundaries (`services/ocr.py:109`).
- **No cross-document or cross-record comparison**, which is central to the target product.

## 7. Correctness and security findings

### 7.1 The ZK circuit is unsound (critical)

`circuits/range_proof.circom`:

- `diff <-- in[0] - in[1]` computes a value without constraining it.
- `is_ge <-- (diff >= 0) ? 1 : 0` is also unconstrained.
- The only constraint is `is_ge * (1 - is_ge) === 0`, which merely makes `is_ge` boolean.
- `out <-- is_ge` is unconstrained relative to the comparison.

A malicious prover can set `is_ge = 1` regardless of `cgpa`. The proof therefore proves nothing about the private value. `GreaterEqThan(n)` ignores `n`, and `CompConstant` is unused. The artifact set should not be trusted until replaced with a constrained comparator (e.g. proper bit decomposition / `LessThan` from circomlib) and regenerated.

### 7.2 Proof verification is not performed server-side (critical)

`routers/verifier.py:57-73` iterates criteria and treats `public_signals[idx] == "1"` as success. It never deserializes the proof, never checks the verification key, and never calls snarkjs or the chain. The integration test demonstrates the bypass: a fabricated proof and arbitrary signals are `APPROVED`.

Even with a correct circuit, signal indexing is wrong: snarkjs orders public signals as outputs first, then public inputs (`[valid, threshold]`), while the endpoint indexes them positionally against criteria.

### 7.3 Cryptographic labeling is incorrect (high)

`attestation.py` and `issuer.py` produce HMAC-SHA256 values but label them `Ed25519Signature2020` with `did:...` verification methods that do not exist. `SECRET_KEY` has a committed default. This is integrity-by-shared-secret, not a verifiable credential signature, and it will not verify in any standard VC implementation.

### 7.4 Blockchain anchoring is incomplete or meaningless (high)

- The backend never submits transactions; `CONTRACT_ADDRESS` and `PRIVATE_KEY` are unused.
- `blockchain_anchor` is a hash string, not a transaction.
- `AstraVerifyAnchor.anchorDocument` has **no access control**: any address can anchor any hash and claim any tier.
- There is no issuer registry, revocation, or mapping from anchor to a verifiable credential.
- The frontend defaults to a Hardhat localhost address; any Amoy deployment requires a manually set `VITE_CONTRACT_ADDRESS`.
- `verifyZKProof` is state-changing solely to emit an event; it is not exposed as a read-only check.

### 7.5 Authentication, authorization, and tenancy (critical)

- No authentication exists anywhere; all endpoints are public.
- No roles, institutions, or ownership checks.
- `GET /digilocker/documents/{aadhaar_last_4}` exposes imported documents to anyone who knows four digits.
- CORS is `allow_origins=["*"]` with `allow_credentials=True` (an invalid/unsafe combination).
- Uploads accept any extension and size; nothing validates document content.

### 7.6 Other reliability issues

- JSON metadata writes are not atomic or concurrency-safe; multiple uvicorn workers would lose records.
- In-memory stores vanish on restart and are per-process.
- `TESSERACT_CMD` defaults to a Windows path on Windows and bare `tesseract` elsewhere; OCR failures are swallowed into `[OCR Error ...]` strings that can then be parsed as data.
- Broad `except` blocks in forensics and OCR hide failures.
- No structured logging, request IDs, rate limiting, or observability.

## 10. Documentation conflicts

1. `README.md` claims an "AI Verification Swarm" with deepfake detection, "cryptographically anchored" credentials, and mathematical privacy guarantees. Sections 5 and 7 contradict this.
2. The README's test flow implies an end-to-end wallet path that is not wired (`ImportOptions` is mocked; proof submission has no handler).
3. `IMPLEMENTATION_ROADMAP.md` is at the repository root, but its deliverables refer to `docs/`, which was empty before this audit.
4. The SIH problem statement itself is **not present in the repository**. Requirement traceability is therefore derived from the roadmap's restatement of it and must be re-validated against the official statement.
5. `frontend/landing/README.md` is the default React+Vite template README and does not describe this project; `frontend/landing/src/App.jsx` is starter content.

## 11. Reuse assessment for the AICTE pivot

### Keep with minimal change
- FastAPI application skeleton and router pattern.
- OCR pipeline (`ocr.py`) as the extraction entry point.
- Storage abstraction (to be backed by a real database/object store).
- Hardhat + snarkjs toolchain, generated verifier, and deployment scripts.
- React shell, routing, and design system.

### Modify substantially
- Upload validation, hashing, and storage (add size/type checks, SHA-256 at intake, atomic persistence).
- Forensics: keep heuristics as advisory signals; remove unsupported claims; add labeled evaluation.
- Orchestrator: convert to evidence-producing findings rather than a single opaque verdict.
- Attestation: replace HMAC with a real signature scheme or clearly label it as an internal integrity checksum.
- Anchor contract: add issuer authorization, revocation, and access control; wire the backend to submit transactions or remove the backend claim.
- DigiLocker: make the simulation explicit, or gate it behind confirmed credentials.
- All three portals: align payloads and replace mock paths with real API calls.

### Build new
- Institution, application, category, checklist, document-version, and rectification models.
- Versioned rules engine with evidence-linked findings.
- Issuer-verification adapter interface and history.
- Anomaly/duplicate detection and infrastructure-evidence workflow.
- Reviewer dashboard, alerts, decisions, and audit trail.
- Authentication, RBAC, institutional isolation, and server-side authorization.
- Database and migrations.
- Real test suite, CI, and evaluation harness.

### Defer or remove
- `frontend/landing/` starter app (decide whether to keep, rebuild, or delete).
- Deepfake detection unless a validated model and labeled data are available.
- `frontend/dist` version control (build artifact; removal requires approval).

## 13. Recommendations for Phase 2

1. Treat the circuit, proof validation, signatures, issuer integrations, and anchoring as **untrusted** until replaced and independently checked.
2. Choose one application category and model the application lifecycle before touching OCR or AI.
3. Introduce a database and authentication early; retrofitting tenancy later is expensive.
4. Make every simulated integration a named, visible adapter (e.g. `SimulatedIssuerAdapter`) with responses labeled in the API and UI.
5. Convert the existing scripts into a real pytest suite with negative, authorization, and contract tests.
6. Remove or clearly mark unsupported claims in all user-facing surfaces.
7. Define measurable acceptance criteria for extraction accuracy and rule outcomes before implementing them.

## 14. Audit limitations

- No dynamic security testing, fuzzing, or dependency vulnerability scan was performed.
- Circuit soundness was determined by source inspection, not by attempting an exploit proof.
- OCR accuracy was not measured against labeled data; only the happy-path sample was exercised.
- The blockchain path was not executed against a running node during this audit; conclusions about it are from source and committed artifacts.
- The official SIH problem statement was unavailable, so requirement coverage is judged against the roadmap's restatement.
- Frontend behaviour was assessed statically; the app was not run in a browser.
